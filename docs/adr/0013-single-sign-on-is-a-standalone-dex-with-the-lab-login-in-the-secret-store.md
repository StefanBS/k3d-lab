# Single sign-on is a standalone Dex, and the Lab login lives in the Secret Store

The Rollouts dashboard and Hubble UI had no login, and ArgoCD and Grafana each had an admin login that was new with every Lab (#74). A login that stays the same has to live where ADR 0003 puts everything that survives a Lab: in the Secret Store. So the Lab has one Lab login, and all that persists of it is its password in the Secret Store. Everything else about single sign-on is rebuilt from Git with each Lab.

- **The provider is Dex**, as a Platform component of its own (`platform/dex`, in the namespace `sso`) at `https://sso.lab.localhost`, with one static user. Nothing of it outlives a Lab: its config is a ConfigMap in Git with no secret in it, and it reads the Lab login's hash and each client's secret from its environment.
- **Dex runs as two instances, which share their state through the Lab's API.** Its signing keys, the logins in progress and its sessions are custom resources in its own namespace, Dex's Kubernetes storage. With in-memory storage each instance has its own, so a sign-in whose requests reach two of them fails, and a UI refuses a token signed by the instance it didn't ask for the keys. Dex creates their CRDs itself as it starts, which is how Dex documents this storage and how its Helm chart runs it. Its ServiceAccount may read and write those resources in `sso`, and create a CRD.
- **The Lab login is `lab@lab.localhost`.** `just host setup` generates its password once, into the Secret Store at `lab/platform/sso/login`. The Secret Store holds only the password; ESO renders the bcrypt hash Dex needs. Dex signs a static user in by email and gives it no groups, so each UI maps its admin role to that email.
- **The Platform's secrets have their own way into the Secret Store.** A second OpenBao role, `eso-platform`, bound to a ServiceAccount of its own, reads only `lab/platform/*`, behind a second `ClusterSecretStore` that only Platform namespaces may use. The `eso` role stays limited to `lab/workloads/*`. It is still one Secret Store.
- **Each OIDC client's secret is in the Secret Store too**, at `lab/platform/sso/clients/<client>`, generated by `just host setup`. Dex and its client run in different namespaces and need the same value.
- **One sign-in opens every UI, because Dex remembers the browser.** Each UI keeps a session of its own, so without that, the Lab login would be typed once per UI. Dex 2.46's auth sessions, experimental and behind a feature flag, answer a second UI's login without the form. They are in Dex's storage like the rest, so they go with the Lab.
- **ArgoCD and Grafana log in through OIDC themselves.** Their local admin logins stay as Break-glass logins, which work without Dex.
- **The Rollouts dashboard and Hubble UI have no OIDC of their own**, so the Gateway asks one oauth2-proxy (`platform/oauth2-proxy`) about each request to them, through a Gateway API `ExternalAuth` filter on their HTTPRoutes. The routes keep pointing at the real Services, and the proxy carries no traffic. Its cookie is set for `.lab.localhost`, so one sign-in opens both.
- **`platform/gateway-api` installs the experimental channel**, the only one with the filter, and is the CRDs' only owner: k3s runs with `--disable=gateway-api-crd`. Its addon installs the standard channel, with a `safe-upgrades` policy that refuses the experimental channel on top.
- **Pods resolve `sso.lab.localhost` to the Server's address**, from a `coredns-custom` ConfigMap. `*.lab.localhost` is loopback inside pods as well (ADR 0003), and the pods that exchange codes for tokens must use the same issuer URL as the browser. The Gateway's Envoy listens on the Server's own network, so that address reaches it from every node.

## Considered Options

- **ArgoCD's bundled Dex**: nothing new to run, but its issuer is under ArgoCD's URL and its config is in `argocd-cm`, so every other UI's login would hang on ArgoCD's chart.
- **Pocket ID**: passkeys only, kept in its own storage, which `just down` destroys unless that storage moves to the Host as well.
- **One Dex with in-memory storage**: no CRDs, no ServiceAccount and nothing written to the Lab's datastore, and how this ADR first had it. But every restart of Dex made new signing keys and forgot every session, and a second instance couldn't be added.
- **Dex's CRDs in Git**, with Dex only checking for them (`crdHandling: check`): Dex needs no right outside its namespace, and ArgoCD owns the CRDs. But nothing upstream publishes them as a file, so the copy is kept by hand, and a Dex update that adds one doesn't start until the copy has it.
- **Authentik or Keycloak**: heavier, each with a database of its own and the same storage problem. Of the five, Dex is the only one whose login survives `just down` through the Secret Store alone.
- **oauth2-proxy in front of every UI**, ArgoCD and Grafana included: saves two client secrets and the Lab CA mounts in ArgoCD and Grafana, though not the CoreDNS entry, but the Gateway's check fails closed and runs before the UI sees a request, so with Dex or oauth2-proxy down the Break-glass logins couldn't be reached either. ArgoCD can't take the user from a header, so it would still ask for its own login after the proxy's. The filter covers a whole route, so Grafana would lose anonymous viewing, and its `auth.proxy` would let anything that reaches its Service without passing the Gateway claim its admin role.
- **The HTTPRoutes pointing at oauth2-proxy**, which then proxies to the UI: works on the standard channel, but every request to a UI goes through the proxy, and each route stops saying which Service it serves.
- **Widening the `eso` role to `lab/platform/*`**: one role and one `ClusterSecretStore`, but any Workload's namespace could then read the Lab login.
- **ESO's `Password` generator for the client secrets**, as for Grafana's admin password: it can't give two namespaces the same value.
- **A CoreDNS rewrite of `sso.lab.localhost` to the Gateway's Service**: the Service's ClusterIP only answers from pods on the Server, so ArgoCD on the other k3d Node timed out. `hostAliases`, the way ESO reaches the Secret Store, would repeat the address in every client's pod.
- **`just up` deleting the `safe-upgrades` policy** and leaving k3s's addon on: k3s would still own a standard-channel copy, and the policy allows going from experimental back to standard, so a k3s update could remove the filter's field, and the login with it.

## Consequences

- The whole Lab runs on Gateway API's experimental channel. Every Verify check passed on it.
- Cilium adds one auth filter to the Gateway's whole https listener, and it fails closed. While oauth2-proxy's one pod restarts, the two UIs behind it answer 403 for about 10 seconds, which is accepted. They have no Break-glass login: with Dex or oauth2-proxy down they can't be opened at their addresses. A `kubectl port-forward` to a UI's Service still reaches it, since it never passes the Gateway. That is no way around the login: whoever can port-forward can already change the Lab with `kubectl`.
- On Cilium 1.20.2, a route with the filter must set `allowedResponseHeaders`, or POST bodies reach the UI cut short (cilium/cilium#48770). Deleting such a route can make the Gateway's other routes answer 403 on open connections (cilium/cilium#49132).
- oauth2-proxy admits anyone Dex signs in, which is right while there is one identity. A second one would need rules there.
- A Workload's UI can opt in with the same filter on its HTTPRoute.
- The client secrets, and oauth2-proxy's cookie secret beside them, outlive a Lab though nothing needs them to. A new client means running `just host setup` again.
- Dex's auth sessions are experimental, so a Dex update can change or drop them. Without them single sign-on still works, with one sign-in per UI.
- Dex writes to the Lab's datastore. Each instance checks its storage every 15 seconds by creating a resource and deleting it, which Dex has no setting for: 16 writes a minute for the two, counted on an idle Lab. On top come a few resources with each sign-in, and the signing keys when Dex rotates them. A restart of Dex, or of one instance, keeps the keys and the sessions. A new Lab starts without either.
- Dex may create any CRD in the Lab, though it can change or delete none. ArgoCD doesn't know of Dex's CRDs: they aren't in Git, and they go with the Lab.
- The Server's address is repeated in one more place in Git, as a pinned Platform fact that lint checks.
